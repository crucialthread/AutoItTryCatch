Concepts

How the Solution Works

Unlike traditional try/catch in languages like C# or Java, this solution does not halt script execution and jump to a catch handler when an exception occurs. The script always continues executing line by line.

The solution works through an exception stack. When an exception is thrown, an entry is added to the current try scope's stack. Functions that are aware of this stack (compatible try/catch functions) check for entries at the start of their execution and skip their work if any exception is already present. This creates the effect of a traditional try/catch: after an exception, subsequent compatible functions are silently skipped until the exception is handled by _Catch().

Important limitation: only compatible try/catch functions and functions decorated with _TryWith(_NoErr() ? ... : Null) skip execution when exceptions are on the stack. Regular AutoIt functions and plain _TryWith(func()) calls always execute regardless of the stack state. This is a fundamental characteristic of the solution that must be understood when designing code that uses it.

Compatible Try/Catch Functions

A compatible try/catch function is the core building block of the solution. It is a regular AutoIt function written with two characteristics:

1. It checks _OnErrorResume() at the start and returns immediately if any exception is already on the stack:

If _OnErrorResume() Then Return SetError(__GetStackCount(), 0, False)

2. It throws named exceptions on failure using the specific pattern:

Return SetError(_ThrowException("ExceptionName", "message", _FunctionName), 0, False)

A complete compatible function looks like this:

_RegisterException("FileException", "A file operation failed")

Func _ReadConfig($sPath)
    If _OnErrorResume() Then Return SetError(__GetStackCount(), 0, False)

    If Not FileExists($sPath) Then
        Return SetError(_ThrowException("FileException", "Config not found: " & $sPath, _ReadConfig), 0, False)
    EndIf

    Return FileRead($sPath)
EndFunc

When called from inside a _Try() block, compatible functions skip automatically if a prior exception is on the stack. When the first one in a chain throws, all subsequent compatible functions in the same scope are skipped, and _Catch() handles the exception.

A compatible function is not limited in what it does - it can contain any number of instructions, perform multiple operations, and throw different exception types depending on what fails at each step. The only requirement is the _OnErrorResume() guard at the top and using Return SetError(_ThrowException(...), 0, False) to signal failures. The example below shows a single compatible function that performs several validation steps and may throw different exceptions: 

_RegisterException("FileException",  "A file operation failed")
_RegisterException("ParseException", "A parse operation failed")

Func _LoadAndProcessConfig($sPath)
    If _OnErrorResume() Then Return SetError(__GetStackCount(), 0, False)

    If Not FileExists($sPath) Then
        Return SetError(_ThrowException("FileException", "Config not found: " & $sPath, _LoadAndProcessConfig), 0, False)
    EndIf

    Local $sContent = FileRead($sPath)
    If @error Then
        Return SetError(_ThrowException("FileException", "Could not read: " & $sPath, _LoadAndProcessConfig), 0, False)
    EndIf

    If StringLen($sContent) = 0 Then
        Return SetError(_ThrowException("ParseException", "Config file is empty", _LoadAndProcessConfig), 0, False)
    EndIf

    If Not StringInStr($sContent, "[Settings]") Then
        Return SetError(_ThrowException("ParseException", "Missing [Settings] section", _LoadAndProcessConfig), 0, False)
    EndIf

    Return $sContent
EndFunc

Integrating Non-Compatible Functions

Many AutoIt built-in functions and third-party UDFs use @error/ SetError() to signal errors rather than participating in the exception stack. Two tools integrate them into the solution:

_TryWith()

Wraps a function call and converts a non-zero @error into a generic exception entry on the stack. @error is captured automatically at the call site - no explicit passing needed: 

_TryWith(FileRead("config.ini"))

Plain _TryWith() always runs regardless of prior exceptions on the stack. It captures the function's own @error independently and throws a generic exception (of type "TryCatchException") if the call failed.

_TryWith() + _NoErr()

Combining _TryWith() with _NoErr() makes a non-compatible function behave like a compatible one - it skips if any prior exception is on the stack: 

_TryWith(_NoErr() ? FileRead("config.ini") : Null)

This is the preferred pattern for wrapping non-compatible functions because it mirrors the behavior of compatible try/catch functions. Use plain _TryWith() only when you specifically want the call to always run regardless of prior exceptions.

The Exception Object

When _Catch() returns True, the output variable is populated with the caught exception entry, exposing three properties:

$e.sExceptionThe exception type name (e.g. "FileException"). Generic exceptions from _TryWith() use "TryCatchException".
$e.sMessageThe exception message.
$e.sSourceThe source of the throw - the function name for compatible function entries, or $UNDEFINED_SOURCE for _TryWith() entries.

Single Match Per Scope

Once a _Catch() call returns True in a given try scope, all subsequent _Catch() calls in the same scope return False. This ensures only one handler runs per scope and makes If/ElseIf chains work as expected: 

Local $e
If _Catch($e, _AsExceptionType("FileException")) Then
    ; this branch runs
ElseIf _Catch($e, _AsExceptionType("NetworkException")) Then
    ; this never runs even if a NetworkException also exists on the stack
EndIf

Latest Entry Wins

When multiple exceptions exist on the scope's stack, _Catch() matches against the latest entry - the one added most recently. Earlier entries remain on the stack but are not returned first.

When using a multi-type list via _AsExceptionType(), list order beats recency - the first type in the list is checked first, regardless of which exception was thrown most recently.

Exception Types and the Registry

Every exception has a name - a string identifier like "FileException". Register exception types with _RegisterException() before using them: 

_RegisterException("FileException", "A file operation failed")

Registration associates the name with a human-readable default message, an optional parent type, and a numeric code. If the message is omitted or empty, it defaults to the exception name itself. Registering an already-registered name overwrites the existing entry.

If you throw an exception name that was never registered, _ThrowException() auto-registers it. Use with care - unregistered names are often typos, and the TryCatchLint tool flags them as warnings.

Exception Hierarchy and Inheritance

Exception types form a tree rooted at "TryCatchException", the root exception type. Every type registered without an explicit parent automatically extends "TryCatchException". You can build deeper hierarchies: 

_RegisterException("IOException",      "An I/O operation failed")
_RegisterException("FileException",    "A file operation failed",    "IOException")
_RegisterException("NetworkException", "A network operation failed", "IOException")

Catching a parent type also catches all descendants. So _Catch($e, _AsExceptionType("IOException")) catches both "FileException" and "NetworkException": 

Local $e
If _Catch($e, _AsExceptionType("FileException")) Then
    ; handle file errors specifically
ElseIf _Catch($e, _AsExceptionType("IOException")) Then
    ; handle any other IOException descendant
EndIf

Using _AsExceptionType()

_AsExceptionType() is the recommended way to pass exception types to _Catch(), even for a single type, as it improves readability and consistency. It accepts a single name, a comma-separated list, or an already-built array: 

; Single type - _AsExceptionType recommended even here
_Catch($e, _AsExceptionType("FileException"))

; Multiple types in one handler
_Catch($e, _AsExceptionType("FileException,NetworkException"))

A bare string is also accepted directly by _Catch(), but _AsExceptionType() is preferred for clarity.

Nested Try Blocks

Try blocks can be nested. Each scope is independent - the inner scope sees only its own exception entries. A _Catch() in the inner scope handles inner exceptions; unhandled entries propagate to the outer scope: 

_Try()                                                    ; outer scope
    _MyCompatibleFunc()

    _Try()                                                ; inner scope
        _TryWith(_NoErr() ? _AnotherFunc() : Null)
    Local $eInner
    If _Catch($eInner) Then                               ; catches inner scope's latest entry
        ConsoleWrite("Inner caught: " & $eInner.sException & @CRLF)
    EndIf
    _EndTry()                                             ; inner scope closed

Local $eOuter
If _Catch($eOuter, _AsExceptionType("FileException")) Then ; catches from outer scope
    ConsoleWrite("Outer caught: " & $eOuter.sMessage & @CRLF)
EndIf
_EndTry()

Force Reset

In rare recovery scenarios - such as test teardown after a deliberately unclosed _Try() - pass $FORCE_RESET to _EndTry() to reset the entire try/catch state regardless of nesting depth: 

_EndTry($FORCE_RESET)
Warning: $FORCE_RESET is for edge cases only. Do not use it as a substitute for properly balanced _Try()/_EndTry() calls in normal code.

Stack Trace

_StackTrace() returns the current scope's exception entries as an array, or passes them through a handler function. The most common usage is to pass _FormatStackTrace as the handler to get a formatted string directly: 

_Try()
    _MyCompatibleFunc()
Local $e
If _Catch($e, _AsExceptionType("FileException")) Then
    ConsoleWrite(_StackTrace(_FormatStackTrace) & @CRLF)
EndIf
_EndTry()
